# author-testcase — Resolved → Test (one issue, end-to-end)

Process **one Resolved CBRD issue end-to-end** into an upstream SQL-TC PR (ready-for-review on a targeted call, Draft on a batch call): Select → Ground → (Author → lint → Review R1, looped) → Verify once → Review R2 → Submit → report. The main session is the **orchestrator**; authoring and reviewing are delegated to separate lanes. It sits **after** [gate-resolved](../gate-resolved/SKILL.md) (which bounces un-plannable issues) and feeds [review-testcase](../review-testcase/SKILL.md). Parallelize independent units (DP1); the TC itself must assert user-observable black-box behavior (DP2 — see Author).

## Scope

**Produces:** one issue processed to an upstream PR (`$FORK:tc/cbrd-XXXXX` → `CUBRID/cubrid-testcases:develop`) — ready-for-review on a targeted call (a named CBRD key), Draft on a batch call (a queue of N issues) — a verified `.sql`+generated `.answer`, and a report at `$HOME/.cubrid-agent/reports/author-testcase/CBRD-XXXXX.md`. Default 1 issue/run; arg = N issues or a specific `CBRD-XXXXX`.

**Does NOT:** merge/approve (human), fire the `Start Test` transition (gate-resolved owns it — author-testcase never writes it), commit to a branch a human has checked out (work **only** on `tc/cbrd-XXXXX` branches in `$TC`), run non-SQL categories, or do the Review pass in the author's context (separate lane — no self-approve).

## Before you start (env — re-establish idempotently every run)

**One call answers this whole section — `~/.cubrid-agent/bin/scout.sh CBRD-XXXXX [--grep <repro pattern>]…`, once, at the start.** It reads (never writes, never touches the network) and reports the environment below, the tree this issue's TC belongs in with a sibling to read, what the corpus already covers, and how far this run has got; when something is absent it **names it and what its absence costs, then stops (exit 3)** rather than letting Verify be the first to find out. Read its answer instead of re-checking these by hand — eight separate look-ups cost eight fixed fees plus the thinking in front of each (CUBRIDQA-1507). Two things it deliberately does not decide: whether the installed build contains **this** issue's fix, and the TC's final path (§3). Runtime is the **$HOME standard** (same resolution as the part-skills); **`/setup-cubrid-agent` (idempotent) provisions it** — run it when the scout names something missing:
- **`$TC`** (testcases clone) = `$CUBRID_TESTCASES` if set, else `~/cubrid-testcases` — with an `origin`(CUBRID) remote and a `fork` remote (your own GitHub fork; `setup-cubrid-agent` adds it). On a machine where that clone is a human's workspace you do **not** need a second clone — §3 isolates into a worktree and hands you the path to use.
- **Identity — read it, never hardcode a person (ADR 0004), never parse `~/.netrc`.** `$QA_USER` = `$CUBRID_JIRA_USER` if exported, else from `source ~/.cubrid-agent/env.sh`; `$FORK` = `$CUBRID_GH_FORK` if set, else `gh api user --jq .login`. Ad-hoc `~/.netrc` parsing returns the hostname or a stale commented-out entry, and one inspection command echoed the real password into a subagent transcript. If you must look at that file, redact **inside the same command** (`grep -A2 'jira.cubrid.org' ~/.netrc | sed 's/password .*/password ****/'`), report only the `login`, and if a secret does leak say so promptly and suggest rotating it (CUBRIDQA-1488). **If either value is empty or `$QA_USER` looks like a hostname, STOP** — an empty value yields a 0-issue queue instead of an error. `select-queue.sh` enforces this, so a batch call is covered; a targeted call skips the queue, and the scout is what covers it — it reads `$FORK` from the clone's `fork` remote with no network call, and stops when either value is missing or doubtful.
- **Build under test** = a CUBRID **release** build at **`$HOME/CUBRID`** that **contains the issue's fix** (the "trusted build"). A **new** issue needs a fix-including build — `/setup-cubrid-agent` (its `--build <url>` step) or `verify-sql` installs one from the build archive (`https://ftp.cubrid.org/CUBRID_Engine/nightly/daily_build`; the internal build server serves the same shape — set `CUBRID_BUILD_BASE` to use it). A build lacking the fix makes `.answer` wrong — never verify on it.
- **env**: `source ~/.cubrid-agent/env.sh` (generated by setup.sh — `.cubrid.sh` + `CTP_HOME` + JDK `JAVA_HOME` + `CUBRID_JIRA_USER`).
- **Run directory — `$HOME/.cubrid-agent/CBRD-XXXXX/`, never `$HOME` or the cwd.** Everything this run produces except the testcase itself goes there: it is already where the manifest lives and where both hooks look. Create it if absent. Short-lived in-step scratch may use `mktemp -d`, but anything the report cites or a human may need afterwards belongs in the run directory. **Do not invent a directory** (`~/scratchpad…`, `~/work…`) — a stray directory in someone's home is indistinguishable from their own files. **Do not delete the run directory on the way out**: a failed run's leftovers are the diagnosis trail.
- **conf**: nothing to do, including under a `$CUBRID_TESTCASES` override — the stock `$CTP_HOME/conf/sql.conf`·`sql_by_cci.conf` already use non-default ports (1822/33120), and `verify-run.sh` writes a copy with `scenario=$TC/sql` into the run directory on every run rather than editing the stock file.
- **cubrid source** for Ground at `~/cubrid` (setup.sh clones if absent). **cubrid-jira** present; **gh holding a token** — the scout reports both, and an unauthenticated gh fails on `gh pr create`, the one command the whole run exists for.
- **Ground the issue with one command (required, during Ground).** `~/.cubrid-agent/bin/ground-issue.sh CBRD-XXXXX` puts the description **and every comment** in the run directory's `issue.txt`, downloads every attachment, records `select.issue_type` (the placement lint needs it), and prints what to read: `read` (text, and extracted archive members), `view` (images — use the Read tool), `unread` **with the reason**. **Read every `read` path and view every `view` path** — the developer's intended cases are attachment-only often enough to decide coverage. **Never infer an `unread` attachment's contents from its filename** (CUBRIDQA-1488); record that it stayed unread. Don't classify attachments by hand — Jira's mimeType lies.
- No build / no CTP env? Do Select→Ground→Author (**including §3's commit** — the work must survive on the branch), leave `.answer` empty, and hand off with `verify-sql` instructions (don't fake verification). **Record the terminal state**: `verify.status="blocked_no_build"` (or `"blocked_no_ctp"`) + `verify.note=<why>` in the manifest, and write the report — without that pair the `gate-stop` reminder keeps firing for gates that can never close.

## Pipeline

```
Select → Ground → ┌─ Author → lint → Review R1 (static) ─┐ → Verify (once) → Review R2 (answer) → Submit → report
                  └──────── cheap loop, no CTP ◄─────────┘         └── only a Verify/R2 finding re-runs CTP ──┘
```

**Cheap gates first, CTP last.** Converge the static review **before** paying for CTP, and let Verify run once. Every review objection in the two measured runs was **static** — regression strength, silent serial fallback, coverage gap, feature-area precedent — and none needed execution output, while the `Author → Verify → Review` order re-ran the whole CTP chain every round (62 min for one issue; the breakdown is in CUBRIDQA-1487).

**Lane handoff — a lane report is a file; only a verdict comes back in the conversation.** Every lane writes its report to a path **you name in its prompt** and returns **its verdict and one line** (the author lane has no verdict — one line); the orchestrator hands the next lane that **path** and never re-reads a report to relay its contents, which cost 2,793 output tokens for two reports in the measured run.
- **Name the file yourself — `$HOME/.cubrid-agent/CBRD-XXXXX/<lane>-<n>.json`**, where `<lane>` is `author`, `review-r1` or `review-r2` and `<n>` is that lane's round from 1 (`author-1.json`, `review-r1-2.json`). **A lane's context is fresh, so it cannot know its own `<n>`** — leave the path to the lane and every round overwrites `author-1.json`, destroying the file the next round is judged against.
- **A lane report is JSON, and its schema is the contract**: `{lane, round, verdict, findings: [{severity, what, why}]}`, plus `preconditions` for the two review lanes (§5). The author lane writes `{lane, round, summary}` and **no verdict**. Reasoning still goes in the string fields — JSON makes it addressable, not shorter. **What a script reads, it can refuse**: `record-preconditions.sh` turns back a review report that dropped `preconditions`, repeated an id, or marked something verified with no evidence — the same omissions in prose were recorded as nothing and read as a clean run. **`verdict` is not yet one of them**: it still reaches the manifest through you, so the §5 failure it names — a lane inventing a third value, submission blocked silently for the rest of the run — is open.
- **The lane's return is the completion signal.** Do not confirm the file with a call of its own, and **never poll for it** — no `sleep`/`seq` loop, no repeated `ls`, no wait with a timeout. The measured run polled the filesystem for up to 20 minutes while already awaiting that same completion, and at ~13s a call a per-round check is the same waste made cheaper.
- **A missing report is a lane failure** — re-run that lane with the path restated; that re-run is not a static round (§6). Do not rebuild the report from what the lane said in the conversation, and do not carry on without one.

**Run manifest (hard gate)**: as each stage completes, record its gate result into `$HOME/.cubrid-agent/CBRD-XXXXX/manifest.json` (schema: [`scripts/manifest.example.json`](../../../scripts/manifest.example.json)). The `lint.*` fields come from the `lint-sql-tc` PostToolUse hook, `select.*`/`ground.*` from the queue and grounding helpers, `verify.*` from `verify-run.sh`/`failpass-run.sh`/`debug-check.sh`/`record-preconditions.sh`; **you** write author / review and the judgments below. Ground before you author — the lint hook reads `select.issue_type` to check the TC's tree, and it runs on the write itself.
- **`verify.status` is one of `passed` | `blocked_no_build` | `blocked_no_ctp` | `blocked_nondeterministic` | `blocked_review_unresolved`.** A `blocked_*` value **requires** `verify.note` (why) plus a written report; that pair is the sanctioned "cannot verify" terminal state which stops the `gate-stop` reminder for a gate that can never close (example: [`scripts/manifest.blocked.example.json`](../../../scripts/manifest.blocked.example.json)). It never makes the run submittable.
- **`verify.preconditions`** holds each condition that decides whether the run proved anything (e.g. "parallelism ≥ 2 or the sort never enters the fixed path"), with its `verified` flag. Put them here, **not in the `.sql` header** — the header ships to the corpus forever (CUBRIDQA-1481). **`record-preconditions.sh` writes this field, never you** (§5). **An unverified precondition means the result is inconclusive**: say so in `verify.fail_to_pass.note` and the report.
- Submit's `gh pr create` is **blocked by the `gate-pr-submit` hook** until the manifest confirms every gate — determinism · fail→pass · `verify.cci.checked` · debug · review PASS · lint · `select.reauthor_reason` (§1) — and the command passes the **generated** body. It names whichever one is missing, so read its denial rather than guessing.

## 1. Select
**One command builds the queue**: `~/.cubrid-agent/bin/select-queue.sh` (`--version <ver>` if the Planned Version is no longer `guava`). It resolves `$QA_USER`/`$FORK`, runs the field JQL, applies the **whole** idempotency screen, prints the queue oldest-resolved-first with a drop reason per excluded key, and records the basis in the head candidate's manifest for the report. **Do not hand-run the screens** — one JQL plus a `gh` lookup per candidate was 13 model turns for a 5-issue queue, and it is now one ~4s call (CUBRIDQA-1487).

It decides only what is mechanical: the field screen (QA Assignee · Planned Version · Resolved · QA Scenario ≠ `Not Required` · not `Duplicate` · not Sub-task) and **already-processed** (a `tc/cbrd-XXXXX` branch on your fork or upstream, an upstream PR from any fork, a local `cbrd_xxxxx` TC dir or branch). Yours is the judgment:
- **Ground and judge ONE candidate at a time, oldest first, stopping at the first that passes** (`~/.cubrid-agent/bin/ground-issue.sh CBRD-XXXXX`, then read `issue.txt`). The batch default is `run=1`, so judging the whole queue to pick one is wasted work — the measured run judged 8 bodies and processed 0. Per candidate: **Reproduction** (concrete SQL/steps in body or comments), **SQL-reproducibility** (observable via SQL alone through the sql-category driver — JDBC, CCI for `sql_by_cci`; no process/config/external-util observation, output identical every run **on the post-fix build**; a probabilistic/race bug is fine if the post-fix output is deterministic — detection power is a Review concern, not a Select gate), and **duplicate by repro** — an existing TC may cover it under another name, which no directory-name screen can see (§2 says how to search).
- **An `INCOMPLETE:` line means a screen could not run** (no `gh` auth, an `ls-remote` failure, unknown fork owner). The queue is still usable, but **say it in the report** — branch-only detection misses a PR opened from someone else's fork, and with several operators that is duplicated work, not a cosmetic gap.
- **Exit 3 = the queue is empty. Say so and stop** — don't silently widen. Broadening Select (another Planned Version or QA Assignee) is the human's decision.
- **The fact that decides the TC's directory** is `select.issue_type`, which **grounding** records from Jira (the queue does not). A `Correct Error` is a bug fix and its TC goes under `sql/_13_issues/`, every other type goes to a release dir — no version field enters that decision. The lint hook cannot see the type from the file, so an ungrounded issue leaves placement **unverifiable**, which blocks submit (CUBRIDQA-1486).
- A Sub-task never enters the batch queue even though `gate-resolved` can pass one to Test (its acceptance criterion is usually a build or a tuning point, not user-observable behavior). Author it by naming it.
- Single issue: `/author-testcase CBRD-XXXXX` skips the queue entirely — **including the already-processed screen**. Redoing a TC on purpose is exactly what that is for, so make it a decision rather than an accident: before authoring, check for a `tc/cbrd-XXXXX` branch (yours and upstream) and an upstream PR, and if one exists and you are redoing it anyway, record why in `select.reauthor_reason`. The submit gate denies the PR when one exists upstream and no reason is recorded. It cannot save you earlier than that: §7's push to your own fork has already updated that PR by the time the gate runs, so the check is yours to make first.

## 2. Ground
Issue content is the source of truth; back it with code facts.
- **Attachments first**: download + read every attachment (per Before-you-start). A `*_testcases.sql`/repro attachment often carries the developer's intended cases (incl. account-switching / multi-session scenarios description misses) — fold them into the case list.
- **The fix commit is already in the manifest** — grounding records `ground.fix_commit`/`ground.fix_pr` from `git log --grep` on `~/cubrid`'s `origin/develop` and prints where to look. Your half is reading it: the fix diff (`git -C ~/cubrid show <sha>`) and the PR discussion (`gh pr view`) are what mark the code path the TC must exercise.
- `$TC`: search existing TCs by **the repro (tables/query pattern, feature area), not the cbrd number** — that is the scout's `--grep`, and the reason it exists is that the same repro may sit under another name (PoC2: `_03_iss_700000`), which no name search sees. If so, **differentiate** (self-sufficient variant that hits the path in the standard suite), don't duplicate.
- **Mark the fix code path** the TC must exercise (feeds Author's path-forcing + Verify's path gate).
- Output: repro scenario, post-fix expected behavior, case list (Author input).

## 3. Author (delegated — create-sql)
- **Where to author is one call, and its answer replaces `$TC` for the rest of the run**: `~/.cubrid-agent/bin/prepare-tc-workspace.sh CBRD-XXXXX` fetches `origin/develop`, puts you on `tc/cbrd-XXXXX` (continuing it on a retry), and prints the path to work in. It authors in the clone when there is nothing to lose, and cuts a worktree when the clone holds uncommitted work or sits on someone's branch — so **never run `git checkout -b` in `$TC` yourself**. From here on that path **is** `$TC` — every later step means it, including §7's `git -C "$TC" …` — and since a shell variable does not survive between calls, **pass `CUBRID_TESTCASES=<that path>` on every helper, CTP and git invocation**. The steps that can locate the branch recover from a forgotten variable on their own — the renderers and §7's check ask git where the branch is checked out, and the submit gate reads the assignment out of the command string itself (an inline `VAR=x` reaches the command, never a hook). **`verify-run`/CTP cannot**, because a conf `scenario=` is a bare path with no branch to ask — forgetting it there runs CTP against the wrong tree. And a run on a **separate clone** with the variable dropped everywhere is beyond all of them: the gate then skips its base check and says so. The scout already checked that `origin` really is `CUBRID/cubrid-testcases`, and stopped if it was not — a hand-made clone can have no `origin` or one pointing at a fork, and then the base is whatever was checked out. The submit gate denies that too, but finding out at submit time wastes the whole run.
- **Delegate with paths, and take a path back.** Give the author lane the workspace path, `issue.txt`, and — on a retry round — the report that sent it back (R1's, or R2's after Verify), each **as a path**; name the file it writes (`author-<n>.json`), and take back one line saying what it wrote or changed. **Never paste a report into the prompt** (Lane handoff, above).
- Author `.sql` **by the `create-sql` skill rules** (header block, `evaluate 'Case N'`, DROP-before-CREATE, self-contained cleanup, English comments, expected values only in `.answer`). **The TC path comes from `create-sql`'s directory convention — do not decide it here.** An orchestrator that fixes the path makes the part skill's rule unreachable, which is how two unreleased bug fixes landed in a release dir (CUBRIDQA-1486). Read the convention and apply it to *this* issue.
- **DP2 (black-box, user-perspective)**: author the TC as a **DBA / DB engineer / AP-developer** would observe the bug — SQL I/O (the sql category runs via the JDBC driver, sql_by_cci via CCI; csql shows a human the same), plan, catalog. Cover boundary + negative cases and field-misuse angles (non-expert), **not** C-internal signals (asserts, page ids) a user can't see. If the fix has no user-observable behavior change (debug-only assert), it's not an SQL-TC target — bounce back to Select judgment.
- `.answer` is **generated by Verify, never hand-written**.
- **Commit before you leave §3.** `git add` the `cases/`+`answers/` pair and commit `[CBRD-XXXXX] Add SQL testcase for <English summary>` + Claude trailer (`.result` is gitignored). Every later stage may legitimately abort — no build (see Before-you-start), 5 rounds exhausted (§6) — and an uncommitted `.sql` is one `git checkout` away from being lost, so the work must already be on `tc/cbrd-XXXXX` before Verify is attempted. On a retry round, amend or add a follow-up commit on the same branch.

## 4. Verify (delegated — verify-sql, local CTP) — **once, after Review R1 says PASS**

**Do not enter Verify until lint is clean and R1 has passed.** This is the only expensive stage — 3 CTP sessions plus, at the end, **four installs**: the debug swap and its restore, then the pre-fix swap and its restore (the debug check added the first pair) — and re-entering it per review round is what turned one issue into 62 minutes.

Run on the fix-including release build; **generate then confirm** the answer. **Do not hand-run any of these chains** — each helper below is one call where the prose used to be many, and [`references/verify-steps.md`](./references/verify-steps.md) carries the reasoning: the session arithmetic, every field each helper records, and why each refusal exists.
1. **answer generation (S1) — two calls, one judgment between them**: `~/.cubrid-agent/bin/verify-run.sh CBRD-XXXXX --generate` prints the output CTP produced; **you** decide whether that is the post-fix behavior the issue states (error code / row count / message); then `--promote` copies it in. Combining the two flags is refused, and so is overwriting an answer that already has content.
2. **confirm + determinism (S2) — one command**: `~/.cubrid-agent/bin/verify-run.sh CBRD-XXXXX --runs 3`. All N `Success:1` = deterministic. Exit 1 = mismatch: **read the diff it printed before concluding the testcase is wrong**. A nondeterministic token (`[Ljava...@hash`, OID, timestamp, ORDER-BY-less multi-row) goes back to Author.
3. **path-coverage gate**: prove the **fix path is actually hit** — a green TC on an unaffected path is worthless. Plan/trace it (`;plan detail`, `.queryPlan`, `SET TRACE ON`) and size the data to clear the thresholds that path needs (under CTP's `test_mode=yes` they are **not** the engine defaults).
4. **CCI cross-check**: `~/.cubrid-agent/bin/verify-run.sh CBRD-XXXXX --runs 1 --category sql_by_cci`. If the CCI output **differs** from the default (JDBC) one, `--promote --category sql_by_cci` writes the `answers/cbrd_XXXXX.answer_cci` sidecar — **never over the JDBC-confirmed `.answer`**. It records `verify.cci.{checked,matches_jdbc}` itself — it just measured the answer, so it does not ask you to retype it — and it no longer overwrites the JDBC run's `verify.determinism`.
5. **debug build check — folded into step 6, one swap phase**: `failpass-run.sh --with-debug-check` orders the installs **pre-fix → fix-debug → fix-release**, so the debug twin is installed **once** and the last install is also the restore: three installs and three CTP runs for three questions, where two separate phases cost four of each. `~/.cubrid-agent/bin/debug-check.sh CBRD-XXXXX` remains for checking debug on its own (it installs the twin and restores release). **`assert` blocks and is not yours to fix** — take the marker and the log to the developer; only a reviewer can accept it as out of this TC's scope (`review.debug_approved` + the note). **`differs` needs an explanation in `verify.debug.note`, not a new answer**: **never promote debug output into `.answer`**.
6. **fail→pass contract — LAST, and exactly once per run**: `~/.cubrid-agent/bin/failpass-run.sh CBRD-XXXXX --prefix-build <version|url> --with-debug-check`. The pre-fix build is the **release** artifact, the same kind the answer was confirmed on; only step 5's twin is a debug build. It writes `confirmed` only for FAIL→PASS; `contradicted` (it passes without the fix ⇒ no regression value) and `inconclusive` both leave submit blocked. **Yours to decide**: that the build you name really predates the fix but follows the feature that introduced the bug, and whether a timing-sensitive race that refuses to reproduce is `best_effort` — which needs `verify.fail_to_pass.note` **and** `review.failpass_approved`. Two actions this cannot decide for you: pin the server to **≥4 cores** when the repro needs parallelism (≤2 disables it, so the bug cannot occur), and with **no pre-fix build available at all**, ground the pre-fix behavior from the issue's Repro/Expected and say that in the note.
- `.answer` is confirmed on the **release** build — that is CI's mode, and it is why a debug run never rewrites it (§5).

## 5. Review (delegated — separate lane, no self-approve) — R1 before Verify, R2 after

Two passes, split by what each actually needs. **R1 needs no execution output** — everything below was raised statically in the measured runs — so it converges before CTP is paid for. **R2 is short and only judges what execution produced.**

**R1 — static (before Verify).** Spawn a **fresh-context review subagent** (opus) and give it **paths, not pasted content** — the issue body, the fix-diff summary and the `.sql` (the `.answer` is still empty — Verify generates it), plus the author lane's report on a re-review, and the path to write its own to (`review-r1-<n>.json`). It judges:
- create-skill self-review checklist (header, evaluate numbering, cleanup, server-message pairing, **placement**);
- **regression value** (would this FAIL on the pre-fix engine?), **coverage** (repro + fix blast radius), **DP2** (asserts user-observable behavior, not internals);
- **whether Verify can even prove anything** — is the data sized to cross the thresholds the fix path needs, is the plan forced (`INDEX_SS`, `recompile`), could the engine silently take a serial/other path and still print the expected counts? Turn each into a `preconditions: [{id, cond}]` entry **in its own report** for §4 to check. This is where the real runs' objections lived (regression strength, silent fallback, coverage gap), and catching them here costs no CTP.
- **Then move them in one call: `~/.cubrid-agent/bin/record-preconditions.sh CBRD-XXXXX --from <that report>`.** It opens each as unverified and names what is still open. It turns the report back if the field is missing (an omission and "this run needs none" are not the same answer — the latter is `[]`) or if one id covers two entries. Copying them across by hand instead is the one relay Lane handoff still had, and it cost more output than the call that replaces it.

**R2 — answer + evidence (after Verify).** Same lane, fresh context, given the paths of the `.answer` Verify generated, the S1–S3 logs, and its own report file (`review-r2-<n>.json`). It judges **only** what did not exist before: **`.answer` validity** (does it match the issue's stated post-fix behavior — not merely "CTP produced it"), the determinism result, and whether each `verify.preconditions` entry came back `verified`. Not a re-review of R1's ground.
- **R2 closes the preconditions R1 opened** — `preconditions: [{id, verified, evidence}]` in its report, then the same `record-preconditions.sh --from` call. It cannot invent an `id` R1 never raised (that means the two lanes are judging different things), and **evidence is required either way**: `verified` without it is an assertion, and a precondition that failed has to say what it measured. Whatever is still open at Submit leaves the result inconclusive — the renderers carry it into the report and the PR body, and you say what it means.
- Output: **`review.verdict` is exactly one of `PASS` | `NEEDS-WORK`** — `PASS` when nothing is left to fix, otherwise `NEEDS-WORK` plus the fix-request list (Author feedback), which stays in the lane report (Lane handoff). Both the submit gate and the stop reminder test `verdict == PASS`, so **inventing any other value (e.g. `READY-FOR-VERIFY`) silently blocks submission and keeps the reminder firing**. **Approval is never in the author's context.**

## 6. Feedback loop — static rounds are cheap, the CTP chain is not
- **Static rounds (Author → lint → R1), up to 5:** loop here until R1 is `PASS`. **Force ≥1 improvement round even on a clean R1** (min 2 static rounds) — the mandate is unchanged, it simply no longer drags a CTP chain behind it.
- **Clear every lint violation before the first CTP run.** The hook fires on the `.sql` write, so a header-length or convention miss is already known — it must never be the reason a chain re-runs, which is exactly what happened once in the measured run.
- **Then Verify once (§4), then R2 (§5).**
- **A second CTP chain needs a Verify or R2 finding to justify it** — nondeterminism, a `verify.preconditions` entry that came back unverified, an `.answer` that contradicts the issue, or a negative fail→pass. Re-run only the sessions the change can affect (an `.sql` edit → S1+S2; a conf/plan problem → S3), and keep fail→pass for after the final `.sql` is settled.
- Submit when all three gates pass (author completeness · verify PASS · review PASS).
- **2 CTP chains without passing** (the first plus one justified re-run — the spec's bound) → the work is already committed on `tc/cbrd-XXXXX` (§3), so keep that branch locally, record `verify.status="blocked_review_unresolved"` + `verify.note=<what still fails>` in the manifest and the skip reason + diagnosis in the report, then move on.

## 7. Submit — push · PR (targeted=ready / batch=Draft)
- The TC is **already committed on `tc/cbrd-XXXXX` by §3**. Now **commit everything the later stages produced** — at minimum the `.answer` that Verify generated and promoted (§3 committed it empty), plus `answers/cbrd_XXXXX.answer_cci` if CCI differed, plus every review-round edit. Confirm nothing is left behind — in two steps, because a failed lookup must read as a stop, not as a clean tree: `TCROOT=$(~/.cubrid-agent/bin/prepare-tc-workspace.sh CBRD-XXXXX)` (it prints the branch's real checkout, so a dropped `CUBRID_TESTCASES` cannot point this at a clone that never held the work; **an empty or failing result is a stop** — `git -C ""` silently means the cwd), then `git -C "$TCROOT" status --porcelain -- '*cbrd_XXXXX*'` must print nothing (**scope by the key**, since a TC directory exists in only one of the two layouts). Then push the branch to the `fork` remote (`.result` is gitignored).
- `gh pr create --repo CUBRID/cubrid-testcases --base develop --head "$FORK:tc/cbrd-XXXXX"` — add `--draft` **only on a batch call** (a queue of N issues); a targeted call (a named CBRD key) opens the PR ready-for-review.
  - **Title**: English, `[CBRD-XXXXX]` header.
  - **Body**: **generate it, do not compose it** — `~/.cubrid-agent/bin/render-pr-body.sh CBRD-XXXXX` writes `$HOME/.cubrid-agent/CBRD-XXXXX/pr-body.md` with the Remarks evidence already filled from the manifest and the `.sql`. **You write only the two `TODO` sections (`### Purpose`, `### Implementation`) and whatever judgment belongs in Remarks** — Korean, user-perspective — and **never retype a number it produced**. Pass it with `--body-file`; the gate denies any other body.
- **Once the PR exists, record it** — `M=$HOME/.cubrid-agent/CBRD-XXXXX/manifest.json; jq '.submitted=true' "$M" > "$M.new" && mv "$M.new" "$M"`. Nothing else writes that field. The triage query in `docs/setup.md` and the stop reminder both read it, and until it is set they read a submitted run as still in flight.
- **Targeted call (a named CBRD key) = ready-for-review PR; batch call (a queue of N issues) = Draft PR.** A human still approves/merges. author-testcase does NOT fire the `Start Test` transition — gate-resolved owns it.

## 8. Report
**Generate it, do not compose it** — `~/.cubrid-agent/bin/render-report.sh CBRD-XXXXX` writes `$HOME/.cubrid-agent/reports/author-testcase/CBRD-XXXXX.md` from the manifest, the `.sql` and git: Select basis (queue counts and what was screened out), Ground summary, case count, **the commit proof** (it asks git whether the `.sql` itself is on the branch and prints "커밋되지 않았다" when it is not, so the report cannot claim work that is not there), Verify numbers, preconditions with their `verified` flag, lint flags, verdict, PR link. **You write only the two `TODO` sections**: the per-round loop history (the one thing the manifest does not hold) and what this run does and does not prove. **Never retype a number it produced** — hand-writing this report cost ~7.9k output tokens, which is time as well as money.

## Note — orchestrator, not author
The main session **drives** the loop and does Select/Ground/Verify/Submit; it **delegates** authoring to `create-sql` and reviewing to a separate subagent. Keep author and review in **different contexts** — a green light the author gave itself doesn't count.
