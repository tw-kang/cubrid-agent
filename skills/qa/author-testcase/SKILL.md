# author-testcase — Resolved → Test (one issue, end-to-end)

Process **one Resolved CBRD issue end-to-end** into an upstream SQL-TC PR (ready-for-review on a targeted call, Draft on a batch call): Select → Ground → (Author → lint → Review R1, looped) → Verify once → Review R2 → Submit → report. The main session is the **orchestrator**; authoring and reviewing are delegated to separate lanes. It sits **after** [gate-resolved](../gate-resolved/SKILL.md) (which bounces un-plannable issues) and feeds [review-testcase](../review-testcase/SKILL.md). Parallelize independent units (DP1); the TC itself must assert user-observable black-box behavior (DP2 — see Author).

## Scope

**Produces:** one issue processed to an upstream PR (`$FORK:tc/cbrd-XXXXX` → `CUBRID/cubrid-testcases:develop`) — ready-for-review on a targeted call (a named CBRD key), Draft on a batch call (a queue of N issues) — a verified `.sql`+generated `.answer`, and a report at `$HOME/.cubrid-agent/reports/author-testcase/CBRD-XXXXX.md`. Default 1 issue/run; arg = N issues or a specific `CBRD-XXXXX`.

**Does NOT:** merge/approve (human), fire the `Start Test` transition (gate-resolved owns it — author-testcase never writes it), commit to a branch a human has checked out (work **only** on `tc/cbrd-XXXXX` branches in `$TC`), run non-SQL categories, or do the Review pass in the author's context (separate lane — no self-approve).

## Before you start (env — re-establish idempotently every run)

Runtime is the **$HOME standard** (same resolution as the part-skills); **`/setup-cubrid-agent` (idempotent) provisions it** — run it if anything below is missing:
- **`$TC`** (testcases clone) = `$CUBRID_TESTCASES` if set, else `~/cubrid-testcases` — with an `origin`(CUBRID) remote and a `fork` remote (your own GitHub fork; `setup-cubrid-agent` adds it). On a machine where `~/cubrid-testcases` is a human's manual workspace, set `CUBRID_TESTCASES` to a separate clone.
- **Identity — read it once, never hardcode a person (ADR 0004).** Both values are per-user. `$QA_USER` = `$CUBRID_JIRA_USER` if already exported, else the one published by `source ~/.cubrid-agent/env.sh` (resolved once by `setup-cubrid-agent`) — **never parse `~/.netrc` yourself**, since its tokens may sit on one line and a commented-out stale entry looks live, so ad-hoc parsing returns the hostname or the wrong user. There is a second reason: an inspection command once echoed the real password into a subagent's tool output before any redaction, putting it in that transcript. If you ever must look at the file, redact **inside the same command** (`grep -A2 'jira.cubrid.org' ~/.netrc | sed 's/password .*/password ****/'`), report only the `login`, and if a secret does leak say so promptly and suggest rotating it (CUBRIDQA-1488). `$FORK` = your TC-fork owner = `$CUBRID_GH_FORK` if set, else `gh api user --jq .login`. Substitute both into the JQL and `gh` commands. **If either is empty or `$QA_USER` looks like a hostname, STOP** and ask the human to export it or run `/setup-cubrid-agent` — an empty value silently yields a 0-issue queue instead of an error.
- **Build under test** = a CUBRID **release** build at **`$HOME/CUBRID`** that **contains the issue's fix** (the "trusted build"). A **new** issue needs a fix-including build — `/setup-cubrid-agent` (its `--build <url>` step) or `verify-sql` installs from the build server (`192.168.1.91:8080`). A build lacking the fix makes `.answer` wrong — never verify on it.
- **env**: `source ~/.cubrid-agent/env.sh` (generated by setup.sh — `.cubrid.sh` + `CTP_HOME` + JDK `JAVA_HOME` + `CUBRID_JIRA_USER`).
- **Run directory — `$HOME/.cubrid-agent/CBRD-XXXXX/`, never `$HOME` or the cwd.** Everything this run produces except the testcase itself goes there: it is already where the manifest lives and where both hooks look. Create it if absent. Short-lived in-step scratch may use `mktemp -d`, but anything the report cites or a human may need afterwards belongs in the run directory. **Do not invent a directory** (`~/scratchpad…`, `~/work…`) — a stray directory in someone's home is indistinguishable from their own files. **Do not delete the run directory on the way out**: a failed run's leftovers are the diagnosis trail.
- **conf**: stock `$CTP_HOME/conf/sql.conf`·`sql_by_cci.conf` already target `${HOME}/cubrid-testcases/sql` on non-default ports (1822/33120) — **no copies needed**. Only if `$TC` ≠ `~/cubrid-testcases`, copy the conf with `scenario=$TC/sql`.
- **cubrid source** for Ground at `~/cubrid` (setup.sh clones if absent). **cubrid-jira** present; gh authenticated (`gh pr view --repo CUBRID/cubrid-testcases`).
- **Ground the issue with one command (required, during Ground).** `~/.cubrid-agent/bin/ground-issue.sh CBRD-XXXXX` (installed by `/setup-cubrid-agent`; if it is missing, run that once rather than grounding by hand) puts the description **and every comment** in the run directory's `issue.txt`, downloads every attachment, and prints what to read: `read` (text, and extracted archive members), `view` (images — use the Read tool), `unread` **with the reason** it could not be read. Read every `read` path and view every `view` path: the developer's intended cases are attachment-only often enough to decide coverage, arriving as a `CBRD-XXXXX_testcases.sql` or as a `.tgz` of cases + answers. **Never infer an `unread` attachment's contents from its filename** (CUBRIDQA-1488) — record that it stayed unread. Don't classify attachments by hand — Jira's mimeType lies (an `.out` answer file served as `application/octet-stream`). The script also records `select.issue_type` from Jira, which the placement lint needs.
- No build / no CTP env? Do Select→Ground→Author (**including §3's commit** — the work must survive on the branch), leave `.answer` empty, and hand off with `verify-sql` instructions (don't fake verification). **Record the terminal state**: `verify.status="blocked_no_build"` (or `"blocked_no_ctp"`) + `verify.note=<why>` in the manifest, and write the report — without that pair the `gate-stop` reminder keeps firing for gates that can never close.

## Pipeline

```
Select → Ground → ┌─ Author → lint → Review R1 (static) ─┐ → Verify (once) → Review R2 (answer) → Submit → report
                  └──────── cheap loop, no CTP ◄─────────┘         └── only a Verify/R2 finding re-runs CTP ──┘
```

**Cheap gates first, CTP last.** A measured run took 62 min for one issue because the loop was `Author → Verify → Review` and every review round re-ran the whole CTP chain — 3 chains plus 4 pre-fix build swaps, and one round existed only to shorten a header the lint hook had already flagged (CUBRIDQA-1487). Every review objection in that run and in the previous one was **static** — regression strength, silent serial fallback, coverage gap, feature-area precedent — none needed execution output. So converge the static review **before** paying for CTP, and let Verify run once.

**Run manifest (hard gate)**: as each stage completes, record its gate result into `$HOME/.cubrid-agent/CBRD-XXXXX/manifest.json` (schema: [`scripts/manifest.example.json`](../../../scripts/manifest.example.json)). The `lint.*` mechanical fields are written by the `lint-sql-tc` PostToolUse hook and `select.issue_type` + `ground.*` by the grounding script; **you** write the rest (author / verify / review + `lint.answer_not_handwritten`). Ground before you author: the lint hook reads `select.issue_type` to check the TC's tree, and it runs on the write itself. **`verify.status` is one of `passed` | `blocked_no_build` | `blocked_no_ctp` | `blocked_nondeterministic` | `blocked_review_unresolved`** — a `blocked_*` value **requires** `verify.note` (why) plus a written report, and that combination is the sanctioned "cannot verify" terminal state that stops the `gate-stop` reminder for gates which can never close (example: [`scripts/manifest.blocked.example.json`](../../../scripts/manifest.blocked.example.json)). It never makes the run submittable. **`verify.preconditions`** is where a condition that decides whether the run proved anything goes — "parallelism ≥ 2 or the sort never enters the fixed path", "the heap must span ≥ 2048 pages" — each with `verified`. Record them here rather than in the `.sql` header: the header ships to the corpus forever, and an instruction to this pipeline does not belong there (CUBRIDQA-1481). An unverified precondition means the result is inconclusive — say so in `verify.fail_to_pass.note` and the report. Submit's `gh pr create` is **blocked by the `gate-pr-submit` hook** unless the manifest confirms determinism · fail→pass · review PASS · lint, **and the command passes `--body-file $HOME/.cubrid-agent/CBRD-XXXXX/pr-body.md`** — the generated body, with its `TODO` sections written and its case count intact. A hand-composed body is denied (§7).

## 1. Select
Queue = Select-passing issues, oldest-resolved first; process `run` arg (default 1).
- **JQL** (anonymous): `project = CBRD AND cf[213834] = "$QA_USER" AND cf[210441] = guava AND status = Resolved AND cf[210565] in ("Required","Not Yet") AND resolution != Duplicate AND issuetype != Sub-task ORDER BY resolved ASC` (substitute the resolved `$QA_USER`). (`cf[213834]`=QA Assignee, `cf[210441]`=Planned Version, `cf[210565]`=QA Scenario — Not Required excluded.)
  - The last two clauses do in one query what body-reading used to do per candidate: a `Duplicate` resolution means the TC belongs to the issue it duplicates, and a Sub-task's acceptance criterion is typically a build or a tuning point, not user-observable behavior. In the measured queue they removed 3 of 8 candidates, and the branch check below removed 2 more — leaving 3 bodies to read instead of 8 (CUBRIDQA-1487). Note the asymmetry this creates: `gate-resolved` can still pass a Sub-task to Test, and the batch queue will never pick it up. That is deliberate, not a bug — such an issue is authored by naming it, `/author-testcase CBRD-XXXXX`.
- **Read the body from the grounded `issue.txt`** — ground each candidate you actually judge (`~/.cubrid-agent/bin/ground-issue.sh CBRD-XXXXX`), never the whole queue. Judge the survivors of the field + idempotency screens **one at a time, oldest first, and stop at the first candidate that passes** — the batch default is `run=1`, so judging the whole queue to pick one is wasted work (the measured run judged 8 and processed 0). Per candidate: **Reproduction** (concrete SQL/steps in body or comments), **SQL-reproducibility** (observable via SQL alone through the sql-category driver (JDBC; CCI for sql_by_cci) — no process/config/external-util observation, output identical every run **on the post-fix build**; probabilistic/race bug OK if post-fix output is deterministic — detection power is a Review concern, not a Select gate), **duplicate** (skip if `tc/cbrd-XXXXX` branch/PR exists or a `cbrd_xxxxx` TC already covers the repro).
- **The fact that decides the TC's directory** is `select.issue_type`, which grounding records from Jira. A `Correct Error` is a bug fix and its TC goes under `sql/_13_issues/`, every other type goes to a release dir — and no version field enters that decision. The lint hook cannot see the type from the file, so an ungrounded issue leaves placement **unverifiable**, which blocks submit (CUBRIDQA-1486).
- **Idempotency — run this BEFORE reading any body.** GitHub is the source of truth: a fork/upstream `tc/cbrd-XXXXX` branch or PR ⇒ already processed ⇒ drop from the queue. One `gh` lookup per key is far cheaper than a body read, and in the measured queue it removed 2 of the 5 survivors. If `gh` is unauthenticated, do **not** drop straight to a local check: `git ls-remote <url> 'refs/heads/tc/cbrd-XXXXX'` needs no credentials on these public repos — run it once against your fork (`https://github.com/$FORK/cubrid-testcases.git`, `$FORK` from `$CUBRID_GH_FORK` when `gh api user` cannot answer) and once against `https://github.com/CUBRID/cubrid-testcases.git`. On an unauthenticated machine that is what surfaces `tc/cbrd-25913` and `tc/cbrd-26799`. Only PR-level detection is lost (a PR whose branch was deleted, or a branch on someone else's fork), so **say in the report that the check was branch-only**. Local branches and `$TC` dirs are the last resort — a local-only check misses an issue someone else already pushed, which with several users means duplicated work.
- **Queue exhaustion**: the JQL can return candidates that are all already-processed or unfit. When the body-judgment + idempotency pass leaves nothing, **say so and stop** — don't silently widen. Broadening Select (other Planned Version / QA Assignee) is a user decision.
- Single issue: `/author-testcase CBRD-XXXXX` (skip the queue).

## 2. Ground
Issue content is the source of truth; back it with code facts.
- **Attachments first**: download + read every attachment (per Before-you-start). A `*_testcases.sql`/repro attachment often carries the developer's intended cases (incl. account-switching / multi-session scenarios description misses) — fold them into the case list.
- `~/cubrid` (fetch, `origin/develop`): `git log --grep=CBRD-XXXXX` → fix commit/PR merge diff; `gh pr view` for PR body/reviews.
- `$TC`: search existing TCs by **the repro (tables/query pattern, feature area), not the cbrd number** — the same repro may exist under another name (PoC2: `_03_iss_700000`). If so, **differentiate** (self-sufficient variant that hits the path in the standard suite), don't duplicate.
- **Mark the fix code path** the TC must exercise (feeds Author's path-forcing + Verify's path gate).
- Output: repro scenario, post-fix expected behavior, case list (Author input).

## 3. Author (delegated — create-sql)
- In `$TC`: fetch `origin/develop`, create branch `tc/cbrd-XXXXX` from it (continue the existing branch on retry; never build on a human's checked-out branch). **Check `origin` actually points at `CUBRID/cubrid-testcases` first** — a hand-made clone can have no `origin`, or one pointing at a fork, and then the base becomes whatever was checked out. The submit gate blocks that (it denies when the branch changes any file outside the TC's own directory), but finding out at submit time wastes the whole run.
- Author `.sql` **by the `create-sql` skill rules** (header block, `evaluate 'Case N'`, DROP-before-CREATE, self-contained cleanup, English comments, expected values only in `.answer`). **The TC path comes from `create-sql`'s directory convention — do not decide it here.** This line used to pin every TC to `sql/_36_guava/cbrd_XXXXX/`, which sent two unreleased bug fixes into a release dir and drew the same review objection on both PRs (CUBRIDQA-1486); an orchestrator that fixes the path makes the part skill's rule unreachable. Read the convention and apply it to *this* issue.
- **DP2 (black-box, user-perspective)**: author the TC as a **DBA / DB engineer / AP-developer** would observe the bug — SQL I/O (the sql category runs via the JDBC driver, sql_by_cci via CCI; csql shows a human the same), plan, catalog. Cover boundary + negative cases and field-misuse angles (non-expert), **not** C-internal signals (asserts, page ids) a user can't see. If the fix has no user-observable behavior change (debug-only assert), it's not an SQL-TC target — bounce back to Select judgment.
- `.answer` is **generated by Verify, never hand-written**.
- **Commit before you leave §3.** `git add` the `cases/`+`answers/` pair and commit `[CBRD-XXXXX] Add SQL testcase for <English summary>` + Claude trailer (`.result` is gitignored). Every later stage may legitimately abort — no build (see Before-you-start), 5 rounds exhausted (§6) — and an uncommitted `.sql` is one `git checkout` away from being lost, so the work must already be on `tc/cbrd-XXXXX` before Verify is attempted. On a retry round, amend or add a follow-up commit on the same branch.

## 4. Verify (delegated — verify-sql, local CTP) — **once, after Review R1 says PASS**

**Do not enter Verify until lint is clean and R1 has passed.** This is the only expensive stage: 3 CTP sessions plus, at the end, two build swaps. Re-entering it per review round is what turned one issue into 62 minutes (CUBRIDQA-1487).

Run on the fix-including release build; **generate then confirm** the answer. **Minimise CTP sessions** — each `ctp.sh` invocation pays ~85s setup (JVM + DB create + server start/stop/delete), while an extra `run` inside a live interactive session is ~1.5s. So the whole Verify is **3 sessions, not ~6**: (S1) generation, (S2) confirm+determinism in one session, (S3) CCI (needs its own conf).
1. **answer generation (empty-answer trick, session S1)**: seed an empty `answers/cbrd_XXXXX.answer` (CTP's interactive `run` skips a case with no answer), run → real output lands in `$CTP_HOME/sql/result/.../cbrd_XXXXX.result`, check it matches intent (error code / row count / message), promote (`cp`) to `.answer`.
2. **confirm + determinism gate (session S2 — single-session N-run)**: run the case **N (=3) times in ONE `ctp.sh --interactive` session** — `printf 'run <case>\n'` repeated N times then `quit`. **All N `Success:1` = deterministic** (run 1 is also the confirm; no separate confirm session). Setup dominates, so N=3 ≈ N=1 in wall time — **keep N=3; never spawn N separate `ctp.sh` (wastes ~3×85s)**. `.result` is overwritten each run, so **N-Success (CTP's masked compare — exactly what regression uses) is the determinism signal, not byte-diffing 3 files**. Nondeterministic token (`[Ljava...@hash`, OID, timestamp, ORDER-BY-less multi-row) → feed back to Author.
3. **path-coverage gate**: plan/trace (`;plan detail`, `.queryPlan`, `SET TRACE ON`) proves the **fix path is actually hit** — a green TC on an unaffected path is worthless (size data to clear thresholds — under CTP's `test_mode=yes` they are **not** the defaults; the three values are in `verify-sql`'s "Config can flip the path").
5. **fail→pass contract — LAST, and exactly once per run.** Install a **pre-fix** build → the TC should **FAIL**; restore the fixed build → PASS. Two installs plus two CTP runs, so it only pays off on the TC you are about to submit: run it **after** S1-S3 and R2 are settled, never once per review round (that alone cost ~12 min of the 62). Race repro is timing-sensitive (best-effort; document the limit); pin the server to **≥4 cores** (≤2 disables parallelism). If no pre-fix build, ground pre-fix behavior from the issue Repro/Expected and note it.
4. **CCI cross-check**: re-run the same `.sql` via `verify-sql` in **sql_by_cci** mode (`run_cci`; stock `$CTP_HOME/conf/sql_by_cci.conf` — copy with `scenario=$TC/sql` only if `$TC` is non-default). If the CCI output **differs** from the default (JDBC) sql output, promote it to `answers/cbrd_XXXXX.answer_cci` (same empty-answer trick); if identical, no `.answer_cci` needed. Record `verify.cci.{checked,matches_jdbc}` — the submit gate requires `cci.checked`.
- `.answer` is confirmed on the **release** build (= CI mode); debug only for diagnosis.

## 5. Review (delegated — separate lane, no self-approve) — R1 before Verify, R2 after

Two passes, split by what each actually needs. **R1 needs no execution output** — everything below was raised statically in the measured runs — so it converges before CTP is paid for. **R2 is short and only judges what execution produced.**

**R1 — static (before Verify).** Spawn a **fresh-context review subagent** (opus) with the issue body, fix-diff summary and the `.sql` (the `.answer` is still empty — Verify generates it). It judges:
- create-skill self-review checklist (header, evaluate numbering, cleanup, server-message pairing, **placement**);
- **regression value** (would this FAIL on the pre-fix engine?), **coverage** (repro + fix blast radius), **DP2** (asserts user-observable behavior, not internals);
- **whether Verify can even prove anything** — is the data sized to cross the thresholds the fix path needs, is the plan forced (`INDEX_SS`, `recompile`), could the engine silently take a serial/other path and still print the expected counts? Turn each into a `verify.preconditions` entry for §4 to check. This is where the real runs' objections lived (regression strength, silent fallback, coverage gap), and catching them here costs no CTP.

**R2 — answer + evidence (after Verify).** Same lane, fresh context, given the `.answer` Verify generated plus the S1–S3 logs. It judges **only** what did not exist before: **`.answer` validity** (does it match the issue's stated post-fix behavior — not merely "CTP produced it"), the determinism result, and whether each `verify.preconditions` entry came back `verified`. Not a re-review of R1's ground.
- Output: **`review.verdict` is exactly one of `PASS` | `NEEDS-WORK`** — `PASS` when nothing is left to fix, otherwise `NEEDS-WORK` plus the fix-request list (Author feedback). Both the submit gate and the stop reminder test `verdict == PASS`, so **inventing any other value (e.g. `READY-FOR-VERIFY`) silently blocks submission and keeps the reminder firing**. **Approval is never in the author's context.**

## 6. Feedback loop — static rounds are cheap, the CTP chain is not
- **Static rounds (Author → lint → R1), up to 5:** loop here until R1 is `PASS`. **Force ≥1 improvement round even on a clean R1** (min 2 static rounds) — the mandate is unchanged, it simply no longer drags a CTP chain behind it.
- **Clear every lint violation before the first CTP run.** The hook fires on the `.sql` write, so a header-length or convention miss is already known — it must never be the reason a chain re-runs, which is exactly what happened once in the measured run.
- **Then Verify once (§4), then R2 (§5).**
- **A second CTP chain needs a Verify or R2 finding to justify it** — nondeterminism, a `verify.preconditions` entry that came back unverified, an `.answer` that contradicts the issue, or a negative fail→pass. Re-run only the sessions the change can affect (an `.sql` edit → S1+S2; a conf/plan problem → S3), and keep fail→pass for after the final `.sql` is settled.
- Submit when all three gates pass (author completeness · verify PASS · review PASS).
- **2 CTP chains without passing** (the first plus one justified re-run — the spec's bound) → the work is already committed on `tc/cbrd-XXXXX` (§3), so keep that branch locally, record `verify.status="blocked_review_unresolved"` + `verify.note=<what still fails>` in the manifest and the skip reason + diagnosis in the report, then move on.

## 7. Submit — push · PR (targeted=ready / batch=Draft)
- The TC is **already committed on `tc/cbrd-XXXXX` by §3**. Now **commit everything the later stages produced** — at minimum the `.answer` that Verify generated and promoted (§3 committed it empty), plus `answers/cbrd_XXXXX.answer_cci` if CCI differed, plus every review-round edit. Confirm nothing is left behind with `git -C "$TC" status --porcelain -- sql/_36_guava/cbrd_XXXXX/` (must print nothing) before pushing the branch to the `fork` remote (`.result` is gitignored).
- `gh pr create --repo CUBRID/cubrid-testcases --base develop --head "$FORK:tc/cbrd-XXXXX"` — add `--draft` **only on a batch call** (a queue of N issues); a targeted call (a named CBRD key) opens the PR ready-for-review.
  - **Title**: English, `[CBRD-XXXXX]` header.
  - **Body**: **generate it, do not compose it** — `~/.cubrid-agent/bin/render-pr-body.sh CBRD-XXXXX` writes `$HOME/.cubrid-agent/CBRD-XXXXX/pr-body.md` in the CUBRID template's shape (jira link + `### Purpose` / `### Implementation` / `### Remarks`; `CUBRID/cubrid-testcases` ships no template of its own), with the Remarks evidence already filled from the manifest and the `.sql`: case count, verification numbers, fail→pass builds, and any precondition left unverified. **You write only the two `TODO` sections and whatever judgment belongs in Remarks** — Korean, user-perspective. Never retype a number it produced: a hand-counted "8 cases" against 7 in the file is a review comment this pipeline already earned (PR #3041). Then `--body-file $HOME/.cubrid-agent/CBRD-XXXXX/pr-body.md`.
- **Targeted call (a named CBRD key) = ready-for-review PR; batch call (a queue of N issues) = Draft PR.** A human still approves/merges. author-testcase does NOT fire the `Start Test` transition — gate-resolved owns it.

## 8. Report
`$HOME/.cubrid-agent/reports/author-testcase/CBRD-XXXXX.md`: Select basis (field values · repro location), Ground summary (fix PR/commit), per-round loop history (verify result · review nits · what changed), final PR link or skip reason. **Before you write that the TC is "on the `tc/cbrd-XXXXX` branch", prove it path-scoped with `git -C "$TC" ls-tree -r --name-only tc/cbrd-XXXXX -- sql/_36_guava/cbrd_XXXXX/` — empty output means the work is NOT committed, so report "not committed" instead.** (`log … -1` is not a proof: the branch is cut from `origin/develop`, so it always shows an unrelated tip commit.) Write the status line last so it cannot contradict the body.

## Note — orchestrator, not author
The main session **drives** the loop and does Select/Ground/Verify/Submit; it **delegates** authoring to `create-sql` and reviewing to a separate subagent. Keep author and review in **different contexts** — a green light the author gave itself doesn't count.
