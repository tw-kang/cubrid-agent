# SQL Testcase Creator (CTP)

Generate well-formed CUBRID CTP SQL testcase files (`.sql` + `.answer`) that follow the conventions of the existing test suite.

## Quick Start

1. Gather context: JIRA issue ID, feature/bug under test, SQL scenarios to cover, expected behavior.
2. Determine directory path based on issue type (bug fix vs. new feature).
3. Generate the `.sql` file following the format conventions below.
4. Generate a placeholder `.answer` file explaining how to populate it.
5. Output both file paths and contents.

## What Makes a Good SQL Testcase

A CTP SQL testcase is a single `.sql` file that sets up schema, exercises the behavior under test across multiple labeled scenarios, then cleans up. CTP runs it via JDBC, captures output, and diffs it against the `.answer` file.

Think of it as: **setup → labeled test cases → cleanup**, all in one SQL file.

## Scope

**What this skill produces:**
- `.sql` test files with proper header, labeled evaluate sections, and cleanup
- `.answer` placeholder (or filled answer if the user provides expected output)
- `.queryPlan` empty file when query plan output is needed in the answer

**What this skill does NOT produce:**
- Shell testcases (see `shell-create`)
- CTP framework modifications
- MEDIUM/JDBC testcases
- Fully populated `.answer` files — answer content must be generated by running the test in answer mode

## Directory Path Convention

### Bug fixes / Issues

```
sql/_13_issues/_{yy}_{1|2}h/cases/cbrd_XXXXX.sql
sql/_13_issues/_{yy}_{1|2}h/answers/cbrd_XXXXX.answer
```

- `{yy}` = two-digit year (e.g., `26` for 2026)
- `{1|2}h` = first half (1h, Jan–Jun) or second half (2h, Jul–Dec) of the year

Example:
```
sql/_13_issues/_26_1h/cases/cbrd_27100.sql
sql/_13_issues/_26_1h/answers/cbrd_27100.answer
```

Multiple test files for the same issue: append a suffix.
```
cbrd_27100_select.sql / cbrd_27100_select.answer
cbrd_27100_update.sql / cbrd_27100_update.answer
```

### New features

```
sql/_{no}_{release_code}/{feature_group}/cases/cbrd_XXXXX.sql
sql/_{no}_{release_code}/{feature_group}/answers/cbrd_XXXXX.answer
```

Example:
```
sql/_36_guava/issue_27000_new_index/cases/cbrd_27000.sql
sql/_36_guava/issue_27000_new_index/answers/cbrd_27000.answer
```

**Note:** Unlike shell tests, multiple SQL test files share the same `cases/` and `answers/` directories within a time period or feature group. Do not create a new subdirectory per test case.

## SQL File Format

```sql
/**
 * This test case verifies CBRD-XXXXX: Brief one-line title
 *
 * Coverage:
 * 1 - Scenario one description
 * 2 - Scenario two description
 * 3 - Edge case description
 */

--+ server-message on

DROP TABLE IF EXISTS tbl_name;
CREATE TABLE tbl_name (col1 INT, col2 VARCHAR(100));
INSERT INTO tbl_name VALUES (1, 'hello'), (2, 'world');

evaluate 'Case 1: description of what this tests';
SELECT col1, col2 FROM tbl_name WHERE col1 = 1;

evaluate 'Case 2: description of expected error';
SELECT col1 / 0 FROM tbl_name;

DROP TABLE IF EXISTS tbl_name;

--+ server-message off
```

### Header block

Always start with a `/** ... */` comment block:
- First line: `This test case verifies CBRD-XXXXX: <title>`
- `Coverage:` section listing numbered scenarios

This is essential — reviewers use it to understand the test intent without reading all the SQL.

### `evaluate` statements

Use `evaluate 'Case N: description'` before each test scenario. This becomes a label in the answer file, making it easy to match output to intent.

- Number cases sequentially: `Case 1:`, `Case 2:`, ...
- Keep descriptions concise but specific: what is being tested and what the expected behavior is

### `--+ server-message on/off`

Enable at the top when the test verifies error messages (e.g., negative tests expecting `-NNN` errors). Always pair with `--+ server-message off` at the end.

Use when:
- Testing that invalid SQL produces specific error codes
- Verifying semantic errors, syntax errors, or runtime exceptions
- Comparing server-side error messages

Skip when: the test only checks result sets with no expected errors.

### Setup and cleanup

- Always use `DROP TABLE IF EXISTS` before `CREATE TABLE` — the test must be re-runnable
- Put all setup at the top, all cleanup at the bottom
- Keep setup minimal: only create what the test actually needs
- Use simple table/column names (`tbl1`, `col1`, `col_a`, etc.) unless the test requires specific names

### Query plan tests

When the test needs to capture query plan output in the answer (e.g., to verify an optimizer decision), create an empty `.queryPlan` file alongside the `.sql` file:

```
cases/cbrd_XXXXX.sql
cases/cbrd_XXXXX.queryPlan   ← empty file, signals CTP to include query plans
answers/cbrd_XXXXX.answer
```

The answer file will then contain `Query plan:` sections after affected SELECT outputs.

## Writing Rules

### SQL style
- Use `DROP TABLE IF EXISTS` before every `CREATE TABLE` in setup
- Use explicit column lists in `INSERT` when it aids readability
- Keep test SQL focused — avoid unrelated joins or complexity that obscures the test intent
- Prefer simple data values (integers, short strings) that make answer diffs easy to read

### Organize by scenario
Use `evaluate` as the sole section marker — do NOT add `-- ===` style comment headers between test cases. The evaluate label itself serves as the section header. A typical test file has 3–10 `evaluate` sections.

### Negative tests (expecting errors)
Enable `--+ server-message on` and write the SQL that should fail. The answer will contain `Error:-NNN` lines with the error message. Do NOT write multiple failing statements without `evaluate` labels — each error case should have its own label for traceability.

### Parameter changes (rare)
If the test requires changing a system parameter for the duration of the test:
```sql
SET SYSTEM PARAMETERS 'param_name=value';
-- ... test ...
SET SYSTEM PARAMETERS 'param_name=original_value';
```

### `holdcas` directive (rare)
For tests requiring transaction hold across CAS reconnects:
```sql
--+ holdcas on;
-- ... transaction-sensitive test ...
--+ holdcas off;
```

## Answer File

The `.answer` file is generated by running the SQL testcase with CTP and copying the resulting `.result` file:

```bash
# 1. CTP로 SQL 테스트 실행
ctp.sh sql -c ~/CTP/conf/sql.conf

# 2. 생성된 .result 파일을 .answer로 복사
cp sql/_13_issues/_26_1h/cases/cbrd_XXXXX.result \
   sql/_13_issues/_26_1h/answers/cbrd_XXXXX.answer
```

CTP가 `.sql` 파일을 실행하면 `cases/` 디렉토리에 `cbrd_XXXXX.result` 파일이 생성됩니다. 이 파일을 `answers/` 디렉토리에 `.answer` 확장자로 복사하면 답안 파일이 됩니다.

**새 테스트케이스 작성 시**: `.answer` 파일은 빈 파일로 생성하거나 아예 생략하고, 실제 CUBRID 환경에서 테스트를 수행한 뒤 `.result` → `.answer` 복사로 완성합니다.

**Answer format (참고용):**
- `===================================================` 가 각 SQL 문의 출력을 구분
- DDL/DML (CREATE, DROP, INSERT): 영향받은 행 수 (`0` 또는 정수)
- `evaluate 'text'`: 레이블 텍스트 출력 후 빈 헤더 행
- SELECT: 컬럼 헤더 + 데이터 행
- 에러: `Error:-NNN\n<에러 메시지>`
- `.queryPlan` 파일이 있으면 SELECT 출력 후 `Query plan:` 섹션 추가

## Generation Process

1. **Clarify the test target**: Confirm the JIRA issue ID, what behavior is under test, and the test type (bug fix or new feature).

2. **Determine the directory path**: Use the current date (year + half) for bug fixes, or ask for the release code for new features.

3. **Draft the `.sql` file**:
   - Write the header comment block
   - Add `--+ server-message on` if testing error conditions
   - Write setup (DROP IF EXISTS + CREATE + INSERT)
   - Write each test scenario with an `evaluate` label
   - Write cleanup (DROP TABLE IF EXISTS)
   - Add `--+ server-message off` if it was enabled

4. **Create the `.answer` file**: Placeholder if running is needed, or filled if output is known.

5. **Self-review before presenting**:
   - Header block present with CBRD issue and coverage list?
   - Every test scenario has an `evaluate` label?
   - Setup uses `DROP TABLE IF EXISTS` before `CREATE TABLE`?
   - Cleanup at the bottom drops everything created in setup?
   - `--+ server-message on/off` paired correctly?
   - `.queryPlan` file needed?

6. **Present the output**: Show both file paths and their contents. If the test scenario is complex, briefly explain the test strategy.
