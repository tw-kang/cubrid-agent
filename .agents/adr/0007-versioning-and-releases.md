# 버전이 전달 단위다 — 배포면을 바꾼 커밋이 자리를 선언하고, `release.sh`가 릴리스를 소유한다

## 배경

2026-08-06 오전에 규칙 없이 릴리스 3개가 나갔다(1.0.0·1.0.1·1.0.2). 그래서 범프를 금지했다. 지금은 고친 것을 팀에 전달할 방법이 없다.

팀원에게 무엇이 도착하는지는 버전 번호가 정한다. Claude Code는 캐시 디렉토리 이름에 버전을 쓴다(`~/.claude/plugins/cache/cubrid-agent/cubrid-agent/<버전>/`). 번호가 그대로면 캐시도 그대로다. CUBRIDQA-1490에서 자동 배달을 4회 측정했다 — 9분, 2분 19초, 24초, 2분 30초. 즉 번호를 올리면 팀원이 아무것도 하지 않아도 도착한다. 번호를 올리지 않으면 커밋을 아무리 쌓아도 도착하지 않는다.

태그도 GitHub Release도 아직 하나도 없다. 그래서 릴리스 사이의 diff를 볼 방법이 없다.

## 결정

**배포면이 범프 대상을 정한다.** 배포면은 사용자 세션 동작을 바꾸는 파일 집합이다(용어 정의는 [CONTEXT.md](../../CONTEXT.md)). 경로 목록의 정본은 `scripts/release.sh`의 `SHIPPED_PATHS` 변수다. 산문에는 포인터만 둔다. 배포면 밖만 바꾼 커밋은 범프하지 않는다.

**자리 규칙**은 셋이다.

- **major** = 팀원이 손을 대야 계속 쓸 수 있다(개명·제거·플래그 변경).
- **minor** = 새 능력이 생긴다(새 스킬·새 플래그·게이트 강화).
- **patch** = 같은 것을 더 올바르게 한다.

**세칙 5개**가 경계를 정한다.

1. 한 릴리스에 여러 유형이 섞이면 최고 자리를 쓴다.
2. 배포면은 1바이트만 바뀌어도 최소 patch다.
3. manifest 호환이 경계다.
4. major에 유예 기간을 두지 않는다. 대신 CHANGELOG에 이행 한 줄을 반드시 쓴다.
5. 배포면은 `skills/qa/` 통짜다. 예외 목록을 두지 않는다.

경계 사례 셋으로 읽는 법을 고정한다.

- 게이트를 더 세게 걸었다 → **minor**. 새 검사가 생긴 것이고, 팀원이 자기 것을 고칠 필요는 없다.
- manifest에 필드를 추가했다 → **minor**. 옛 run 디렉토리를 그대로 읽는다.
- 옛 run 디렉토리를 더 못 읽는다 → **major**. 팀원이 실행 상태를 버려야 계속 쓴다.

**자리를 변경 시점에 선언한다.** 배포면을 바꾼 커밋은 같은 커밋에서 CHANGELOG `[Unreleased]`에 항목을 추가한다. 항목마다 자리 태그를 붙인다. 릴리스 자리는 쌓인 태그의 최댓값이다. 사람은 릴리스 시점에 다시 판단하지 않는다. 태그를 어떻게 적는지는 `AGENTS.md`가 지시하고, `release.sh check`의 검사 ⑥이 강제한다.

**릴리스 트리거는 3종**이고, 에이전트가 충족 시 자율 실행한다.

1. 팀원이 기다리는 결함 수정은 즉시 릴리스한다.
2. 기능이 완결되면 그 자리에서 릴리스한다.
3. 그 외에는 쌓는다. 단 `[Unreleased]` 체류가 7일을 넘지 않게 한다.

릴리스 커밋의 메시지에 트리거 번호를 남긴다. 그러면 왜 지금 나갔는지가 이력에 남는다.

경고 — 범프 커밋은 반드시 `develop`을 경유한 뒤 `main`으로 간다. 순서를 뒤집으면 기존 설치자의 갱신이 조용히 끊긴다. 그 이유와 브랜치 모델은 [ADR 0008](./0008-branch-model-prs-and-work-tickets.md)이 소유한다.

**`scripts/release.sh`가 버저닝 도메인을 단독으로 소유한다.** 모드는 셋이다.

- `check` — 아래 검사 8건을 돌린다.
- `next` — 다음 릴리스의 버전과 자리를 계산해 출력한다. 아무것도 바꾸지 않는다.
- `run --trigger <1|2|3>` — 릴리스를 3단계로 수행한다. 범프 후 `develop` push, `develop`→`main` PR 일반 merge, 태그와 GitHub Release다.

계산부와 실행부를 나눈다. 그래야 테스트가 계산부를 오프라인으로 검증한다.

**check 모드의 검사는 8건**이다.

1. version 선언이 있다.
2. semver 형식이다.
3. CHANGELOG 최신 날짜 절과 일치한다.
4. 날짜가 ISO 형식이다.
5. `package.json` 버전이 같다.
6. `[Unreleased]` 항목에 자리 태그가 있다.
7. 배포면이 마지막 릴리스 뒤에 바뀌었으면 `[Unreleased]`가 비어 있지 않다.
8. 최신 절의 버전 증분이 그 절의 최고 태그와 같다.

검사 둘은 조건이 갖춰져야 성립한다. 검사 7은 git 이력을 읽으므로 shallow clone이나 태그 부재에서는 건너뛰고 사유를 출력한다. 그래서 CI는 전체 이력과 태그를 받도록 checkout한다 — 기본 depth 1로 두면 이 검사가 영원히 조용히 지나간다. 검사 8은 앞선 릴리스가 있어야 증분을 잴 수 있으므로 첫 릴리스에서는 건너뛴다.

**도구 하나에 테스트 하나를 둔다.** `scripts/test-plugin-version.sh`를 삭제하고 그 검사를 check 모드로 흡수한다. `scripts/test-release.sh`가 `release.sh`의 1:1 짝이다. 스크립트 순증은 1이다.

**1.0.0으로 통합한다.** 1.0.1과 1.0.2는 선언된 버전으로 배달됐다. 다만 태그도 GitHub Release도 남기지 않았다. 그래서 지울 것은 CHANGELOG의 절 둘뿐이다. 셋을 하나의 `1.0.0`으로 다시 쓰고 `v1.0.0` 태그 하나만 만든다. 되돌리는 것이 아니라 다시 쓰는 것이다.

그래서 **다음 릴리스는 minor 이상으로 낸다.** patch로 내면 1.0.1이고, 그것은 1.0.2를 이미 받은 설치본보다 낮은 번호다. 이 제약은 1.0.0 다음 한 번만 적용된다.

경고 — 이미 1.0.1이나 1.0.2를 받은 설치본은 더 낮은 번호를 갱신으로 보지 않을 수 있다. 옛 내용이 든 1.0.0 캐시가 남아 있으면 그것을 조용히 재사용하기도 한다. 처방은 하나다 — 캐시를 지우고 다시 깐다. 팀원이 2026-08-06 오전에 1.0.x를 설치했을 확률은 낮지만 0이 아니다. 그 문의는 CUBRIDQA-1505로 받는다.

## 근거

- **번호가 곧 배달이다.** 실측 4회가 보여주는 것은 그것 하나다(CUBRIDQA-1490). 그래서 규칙이 정할 것도 "언제 올리나" 하나다.
- **변경한 사람이 자리를 가장 잘 안다.** 릴리스 시점에는 커밋 여러 개의 성격을 되짚어야 한다. 변경 시점에는 자기 diff 하나만 보면 된다.
- **선언을 기계가 강제한다.** 검사 ⑥과 ⑦이 없으면 태그 없는 항목과 항목 없는 배포면 변경이 그냥 지나간다. 사람이 지키는 규약을 스크립트가 판정하는 사실로 옮겼다(DP6).
- **경로 목록은 코드에 둔다.** 검사 ⑦이 그 목록으로 diff를 판정한다. 산문에 사본을 두면 판정과 문서가 갈라진다(DP7-2).
- **릴리스를 스크립트 한 번으로 만든다.** 그러면 절차 이탈이 구조적으로 불가능하고, 에이전트가 사람 없이 실행할 수 있다.

## 이 결정이 바꾸지 않는 것

- **로드 대상 6종과 상시 비용** — [ADR 0001](./0001-repackage-as-plugin.md)·[ADR 0006](./0006-shipped-vs-in-progress-skill-trees.md) 그대로다. 버저닝은 무엇이 로드되는지 정하지 않는다.
- **배포면 밖의 변경** — 문서·규범·테스트·`skills/in-progress/`만 고친 커밋은 버전을 만들지 않는다. develop에 그대로 쌓인다.
- **캐시 경로 규칙** — Claude Code가 정한다. 우리가 정하는 것은 번호뿐이다. 그래서 번호를 낮추는 일이 위험하다.

## Considered Options

- **changesets 툴체인 도입**: 변경마다 파일 하나를 남기므로 병렬 PR이 CHANGELOG에서 충돌하지 않는다. 기각 — node 의존이 생기고, 이 규모에 과하다. 충돌은 두 항목을 모두 남기면 풀린다.
- **현행 유지(커밋 SHA를 버전으로 둔다)**: 규칙이 필요 없다. 기각 — 실측이 전달 실패를 보여준다. 번호가 그대로면 캐시 디렉토리가 그대로고, 설치본은 옛 내용을 계속 읽는다.
- **릴리스 시점에 자리를 판단**: 커밋이 가벼워진다. 기각 — 매 릴리스마다 기억을 되짚어야 하고, 그 판단은 검증할 수 없다.
- **`test-plugin-version.sh`를 두고 `release.sh`를 새로 추가**: 변경이 가장 적다. 기각 — 버전 검사가 두 곳으로 갈리고, 도구 하나에 테스트 하나 규범이 깨진다.

## Consequences

- `scripts/release.sh`와 `scripts/test-release.sh`가 생기고 `scripts/test-plugin-version.sh`가 사라진다. 스크립트 순증은 1이다.
- 버전 상태는 `check-invariants.sh`가 아니라 `release.sh check`가 판정한다. CI가 두 브랜치에서 이것을 돌린다.
- CHANGELOG를 단일 `[1.0.0]` 절로 다시 쓰고, `plugin.json`·`package.json`을 1.0.0으로 맞추고, 범프 금지 문구를 지운다.
- 설치본 2곳(dev·dryrun_agent)을 제거하고 다시 깐다. 옛 내용의 1.0.0 캐시가 남아 있기 때문이다.
- 브랜치·PR·티켓 규칙은 ADR 0008이 잇는다. 티켓: CUBRIDQA-1508.
